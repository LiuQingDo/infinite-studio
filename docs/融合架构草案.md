# 图片创作平台融合架构草案

## 已确定的方向

- 面向海外用户，以多个专业领域的图片生成为主要目标，视频生成为辅助能力。
- 采用路线 C：以目标产品架构为主体，分别评估并吸收 infinite-canvas 和 Toonflow 的适用能力，不预先将任一上游作为最终主体。
- 产品与技术方案尚需实际验证；本草案不代表功能已实现、已测试或可以上线。

## 目标体验

用户按任务进入图片创作，例如商品图、品牌视觉或角色内容；生成后的图片可继续编辑、复用和管理。画布用于需要多素材和多步骤的创作，简单任务的入口和流程仍需设计。具体行业、首批场景与功能边界尚未确定。

## 融合原则

1. 以用户任务和实际效果决定功能，避免重复建设两个项目已有的相同能力。
2. 对画布、素材、模型接入和任务状态分别定义清晰边界，避免同时维护两套不兼容的实现。
3. 同一功能先在两边对照实际行为，再选择沿用、改写或重新实现；功能存在不等于已验证效果。
4. 遵守所选来源的许可、版权和第三方依赖要求；记录来源与具体版本。

## 架构候选与约束

React/TypeScript 是画布实现的候选方案；最终框架、页面组织、数据模型和部署方式均待比较决定。可以研究独立服务处理账户、文件和异步生成，但这与当前项目“外部请求由浏览器直连、不假设项目后端”的规则不同，只有在方案明确并更新项目约定后才能实施。参考版本中的画布与“我的素材”主要保存在浏览器本地；本站尚无账户作品或云同步功能。

面向公开网站时，候选方案需要分别验证身份认证、用户数据隔离、模型密钥管理、任务恢复、作品存储、成本与日常运维。视频按产品优先级后续评估，不预设首轮纳入。

## 下一步比较

在条件可比时，分别用两个项目验证：

1. 商品图换背景，检查商品外观与边缘保留。
2. 使用角色参考图连续生成，检查主体特征与结果复用。
3. 局部修改图片，检查选区外内容与边缘衔接。

记录所用版本、模型和参数，区分界面行为、模型效果与实际费用；再比较可访问性、英文体验、可维护性和许可。验证依赖的模型账号、测试素材及成本尚未确定，不把静态源码阅读当作实测结论。
