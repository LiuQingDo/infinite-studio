# AI 创作工具市场与开源竞品调研

调研日期：2026-10-30。目的：为 Infinite Studio 寻找有证据支持的差异化方向，而不是直接将功能清单当作创新。

## 方法和限制

- 围绕 AI 图片创作、自部署、无限画布、资产与工作流，检索 GitHub 项目及文档、LINUX DO 帖子和 GitHub issue；重点核对当前集成的 Infinite Canvas 及其二开版本。
- 下文的功能说明主要来自项目 README、作者发帖或 issue，属于**公开自述或个案反馈**，不是本次独立安装实测。部分 issue 已解决，不能当作当前版本仍存在的 bug。
- 这是有针对性的竞品扫描，不是穷尽全市场，也没有用户访谈、系统抽样、留存或市场规模数据。出现一个 issue 只能证明有人提出问题，不能证明需求普遍或竞争对手都无法满足。
- 公开页面和项目变化很快，版本、功能、授权、维护状态应在选型或发布前重新核验；相关外部模型、内容和素材可能有独立许可。

## 核心结论

1. 无限画布、接入多模型、提示词库、素材管理、Agent、可自部署、方案复用，都已有不同成熟度的同类项目。单个功能名称难以支撑“首创”叙事。
2. 对本项目最直接的机会，是面向**已经在 NAS 或自托管环境使用 AI 画布、希望长期保管项目的个人创作者**，把可挂载存储、迁移、备份恢复、后台任务和可解释的模型接入做成一个经验证的整体。上游有人明确提出此需求，且 issue 标为不计划；但其他二开项目已宣称支持服务端持久化，因此这是定位和体验机会，不是无人占据的空白。
3. 版本树、资产卡、方案包可以作为服务该场景的后续能力；竞品已有素材池、项目、工作流模板等相近能力，本次没有证据证明这些功能本身独特，也没有证据证明它们比可靠存储更受用户重视。
4. 推荐先做有限竞品实操和用户验证，再确定是否独立维护产品、与上游协作，或专注做存储/迁移能力；当前证据不足以断言哪条方案一定成功。

## 用户与开发者反馈：证据而非市场规模

### 1. NAS 和浏览器数据边界

[Infinite Canvas issue #159](https://github.com/basketikun/infinite-canvas/issues/159) 的提出者在 NAS/Docker 部署后，希望画布、素材、生成记录及配置存入挂载目录，以便长期持久化、备份和恢复。该 issue 标记为 **closed as not planned**。同项目 README 说明默认数据位于浏览器本地，并提醒历史数据兼容性不保证。

判断：这是与用户目标高度一致的、可核查的具体需求；但一条 issue 不证明需求规模，也不代表浏览器存储对所有用户都不好。TigerOWO 二开版本已介绍后端同步，应实际验证其存储位置、备份与迁移，再比较差距。

### 2. 模型与中转站的兼容性

[Infinite Canvas issue #55](https://github.com/basketikun/infinite-canvas/issues/55) 记录 Gemini 原生请求协议与 OpenAI 图片接口不同；维护者随后表示已增加支持并关闭。它说明“OpenAI 兼容”并不等于各种模型都能使用完全相同的请求，也说明项目已处理该具体问题。

[ProductFlow 的 LINUX DO 帖](https://linux.do/t/topic/2068263)中有用户报告特定中转出现 400，作者解释参数及协议适配问题；这是历史个案，不应推断目前仍未解决。[Infinite Canvas 功能文档](https://github.com/basketikun/infinite-canvas/blob/main/docs/content/docs/overview/features.zh-CN.mdx) 也说明了不同图片、文本和视频调用路径。

判断：可维护的能力清单、可理解的报错和公开兼容测试有潜在价值，但模型适配本身已经是众多项目的基础能力，不能单凭“支持多模型”称作创新。

### 3. 生成成功与本地保存成功是两件事

[Infinite Canvas issue #149](https://github.com/basketikun/infinite-canvas/issues/149) 记录了供应商已生成图片，但跨域下载/本地保存失败被展示为生成失败的情况。该问题后被标记已完成。它说明需要区分上游生成、下载、持久化三个状态；出现不确定结果时不能盲目再次提交，以免重复消耗。

判断：这是可靠性设计的具体切口，不是尚未有人解决的问题。应通过针对实际接口的故障注入和用户体验验证判断产品价值。

### 4. 安装和交互摩擦

[Linux.do 自部署求助帖](https://linux.do/t/topic/2358308)中用户希望更简单的部署方式；[另一个讨论](https://linux.do/t/topic/2527399)提出分辨率配置需求。[Scumble 用户讨论](https://www.reddit.com/r/comfyui/comments/1wslb6r/scumble_a_free_inpainting_editor_that_runs_on/)出现图层选择和操作体验反馈。

判断：这些是单独场景中的反馈，足以作为可用性测试任务，不足以推断市场占比或所有工具的质量。

## 可选择的产品方向

### A. 可自托管、数据可靠的图片创作工作台——优先验证

**目标用户**：希望自备模型接口、在 NAS 或个人服务器运行，长期保存画布和图片的个人创作者。

**要解决的具体任务**：用户换浏览器或设备后仍能找回项目；升级前后可核对画布和素材；模型中断时知道是提交、下载还是保存失败。

**最小可验证方案**：

1. 自部署服务和可配置持久化目录；画布项目、素材、生成记录存入部署机，不把浏览器缓存作为唯一副本。
2. 从当前浏览器导出、预览并导入旧项目；保留原始数据、可重复导入且避免静默覆盖。
3. 在独立目录演练备份恢复，校验画布、素材引用、记录；默认不导出密钥。
4. 先支持少量明确列出的供应商协议，记录能力差异；区分提交、生成、下载、保存等状态，未知结果不得盲目自动重试。
5. 验证同一台服务被两个浏览器访问后的数据一致性和安全边界。首版默认单用户/可信环境，不把同步等同于安全的公网多用户服务。

**差异化假设**：如果能将这些能力做成简单、可观察、可恢复且文档可信的体验，可能吸引上游浏览器本地模式不满足需求的人。需要与 TigerOWO 等项目实测后才知道差距是否足够大。

### B. 特定创作场景的端到端流程——备选

面向商品视觉或角色系列设计，围绕素材、参考图、结果对比与交付提供预设流程。ProductFlow、Reveric 等已有相邻场景，不能仅凭资产卡或角色管理判断机会；应先找到可接触的具体用户群、同一个真实任务和可衡量的改进，再比较现有项目。

### C. 跨工具的创作归档与迁移——备选

聚焦项目导出、恢复、素材引用、来源和已知生成参数，探索与 Infinite Canvas、ComfyUI 等格式互操作。这与本地数据目标一致，但具体支持哪些格式、是否可无损导入、是否足够独立，需要检查各工具实际数据结构并试做；不宣称能统一或完全复现所有模型。

## 下一步验证建议

先选上游 Infinite Canvas、TigerOWO 二开和 Nova Image Studio，按同一测试表在隔离环境完成：干净安装；创建包含多图和参考关系的画布；重启与换浏览器；导出、恢复；设置一个兼容接口；模拟生成成功但保存失败。记录项目版本、系统、操作步骤、时间、结果及截图。测试前审查容器和脚本，不使用真实密钥或真实私有数据。

然后邀请 5—8 位 NAS/自部署图片创作者完成同一套真实任务，记录失败点、恢复次数以及是否继续使用；这是初步可用性研究，不构成有统计代表性的市场调查。若竞品已完整覆盖，或用户并不认为问题值得切换，应停止把该点作为主打，重新选择具体场景。

本调研未对竞品安装或做生成实测，也未进行访谈；以上产品方向是基于公开资料的待验证假设，不是已决定的发行承诺。
